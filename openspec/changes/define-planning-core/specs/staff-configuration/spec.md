## Purpose

Permet au restaurateur de décrire son établissement : équipes, rôles à niveaux, employés (contrat, indisponibilités, bien-être) et rattachement des comptes via un code d’invitation.

## ADDED Requirements

### Requirement: Teams are salle or cuisine
The system SHALL represent each employee and each role as belonging to exactly one team: salle or cuisine.

#### Scenario: Assign employee to kitchen
- **WHEN** the restaurateur creates an employee with team cuisine
- **THEN** that employee is only eligible for cuisine posts and cuisine service structures

### Requirement: Roles have ordered skill levels per team
The system SHALL let the restaurateur define, per team, named roles each with an integer skill level. A higher level is able to perform any lower-level post on the same team. The system MUST explain this substitution rule when the restaurateur enters roles.

#### Scenario: Kitchen ladder
- **WHEN** the restaurateur records chef 4, sous-chef 3, commis 2, plongeur 1 for cuisine
- **THEN** those four roles exist on the cuisine team with those levels and the substitution explanation has been shown

### Requirement: Employee contract profile
The system SHALL store for each employee: name, role, skill level, team, and contractual hours per week.

#### Scenario: Create a commis
- **WHEN** the restaurateur creates an employee named Sam, role commis, level 2, team cuisine, 35 contractual hours
- **THEN** the employee profile contains those values

### Requirement: Recurring and service unavailabilities
The system SHALL record employee unavailabilities as restaurateur-stated constraints, including patterns such as every morning, every given weekday, or specific services.

#### Scenario: Every Tuesday off
- **WHEN** the restaurateur marks an employee unavailable every Tuesday
- **THEN** that employee MUST NOT be assigned to any Tuesday slot unless the restaurateur overrides and accepts the resulting warning

#### Scenario: No morning services
- **WHEN** the restaurateur marks an employee unavailable for all morning services
- **THEN** that employee MUST NOT be assigned to a morning service unless overridden with a warning

### Requirement: Wellbeing preferences
The system SHALL record, per employee, the following wellbeing preferences (others MAY be added in a later change): prefer two consecutive rest days; one weekend off every two weeks; at least one rest day each weekend; no evening service; no morning service; at most two coupures per week; at most three coupures per week.

#### Scenario: Consecutive rest days preference
- **WHEN** the restaurateur enables “two consecutive rest days” for an employee
- **THEN** the constraint engine treats that preference as a souhait-level constraint for that employee

### Requirement: Restaurant invite code
The system SHALL let the restaurateur generate an invite code from the interface. When an employee creates an account with that code, the system MUST link the account to that restaurant.

#### Scenario: Employee joins with code
- **WHEN** an employee creates an account using a valid invite code generated by the restaurateur
- **THEN** the account is linked to that restaurant and can see that restaurant’s published planning

### Requirement: Restaurateur owns constraints in v1
The system SHALL treat all staff constraints in this version as entered by the restaurateur. Employee-originated constraint edits are out of scope; the same engine MUST still apply when those constraints later change source.

#### Scenario: Only restaurateur edits unavailability
- **WHEN** an employee is linked via invite code
- **THEN** unavailabilities and wellbeing preferences for that employee are only writable by the restaurateur
